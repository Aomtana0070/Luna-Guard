# Luna Guard
## ข้อกำหนดผลิตภัณฑ์ด้านความปลอดภัย

> **เอกสารฉบับปรับปรุง** · 1.2 · 11 ตุลาคม 2026  
> **ขอบเขตหลัก:** Windows Desktop · **แพลตฟอร์มเสริม:** Android และ iOS companion app  
> **สถานะ:** เอกสารข้อกำหนดและข้อเสนอแนะสำหรับการพัฒนา ไม่ใช่การรับรองความปลอดภัยหรือผลตรวจสอบโค้ดฉบับปัจจุบัน

Luna Guard มีเป้าหมายช่วยตรวจสอบไฟล์และสัญญาณความเสี่ยง อธิบายหลักฐานให้ผู้ใช้เข้าใจ และจัดการรายการที่น่าสงสัยอย่างระมัดระวัง โดยต้องไม่กล่าวอ้างเกินขอบเขตความสามารถจริง

> **หลักการสำคัญ:** ตรวจจับอย่างชัดเจน · อธิบายอย่างซื่อตรง · จัดการอย่างปลอดภัย

## สรุปสำหรับผู้บริหาร

Luna Guard ควรพัฒนาจากเครื่องมือตรวจสอบความปลอดภัยแบบ open source ไปสู่ผลิตภัณฑ์ที่น่าเชื่อถือ โดยให้ความสำคัญกับความถูกต้อง ความปลอดภัยในการจัดการไฟล์ ความโปร่งใสของผลตรวจ และการใช้งานที่เข้าใจง่าย มากกว่าการเพิ่มจำนวนฟีเจอร์เพียงอย่างเดียว

### เป้าหมาย

1. ตรวจสอบไฟล์และสัญญาณที่เกี่ยวข้องด้วยหลายแหล่งหลักฐาน เช่น SHA-256, YARA และ IOC
2. แสดงให้ชัดว่าตรวจอะไรแล้ว ไม่ได้ตรวจอะไร และมีส่วนใดที่ไม่สำเร็จ
3. อธิบายเหตุผลและแหล่งที่มาของการตรวจพบโดยไม่ทำให้ผล heuristic ดูเหมือนการยืนยันมัลแวร์
4. กักกันไฟล์อย่างปลอดภัย ตรวจสอบความถูกต้องก่อน Restore และไม่ลบไฟล์โดยอัตโนมัติ
5. เก็บประวัติและบันทึกเหตุการณ์โดยไม่เปิดเผยข้อมูลลับหรือเก็บข้อมูลเกินจำเป็น
6. ใช้งานร่วมกับ Microsoft Defender โดยไม่อ้างว่าใช้แทนการป้องกันแบบ real-time

### หลักตัดสินใจที่ต้องยึด

| หลักการ | ข้อกำหนด |
|---|---|
| ไม่กล่าวอ้างเกินจริง | ห้ามใช้คำว่า “ปลอดภัย 100%”, “ตรวจพบทั้งหมด” หรือ “แทน Antivirus ได้” |
| อ่านอย่างเดียวเป็นค่าเริ่มต้น | การสแกนต้องไม่แก้ไขไฟล์ต้นฉบับ |
| กักกันก่อนจัดการ | ผลตรวจพบไม่ควรนำไปสู่การลบไฟล์โดยอัตโนมัติ |
| หลักฐานต้องตรวจสอบได้ | แสดงชนิดกฎ แหล่งข้อมูล เวลา และข้อจำกัดของผล |
| ความล้มเหลวต้องมองเห็นได้ | ห้ามแสดงผลสำเร็จสมบูรณ์หากมีส่วนสำคัญที่ข้ามหรือสแกนไม่สำเร็จ |
| เคารพขอบเขตแพลตฟอร์ม | Windows, Android และ iOS มีสิทธิ์และความสามารถในการตรวจต่างกัน |

### ลำดับงานที่แนะนำ

1. ทำ Quarantine และ Restore ให้ทนต่อการปิดโปรแกรม/ไฟดับ และตรวจสอบ hash ได้
2. จำกัดและป้องกัน Local API รวมถึงขอบเขตการอ่าน Archive
3. ทำให้ build, dependency และ release ตรวจสอบย้อนหลังได้
4. ปรับผลตรวจ ประวัติ และหน้ารายละเอียดให้เข้าใจง่าย
5. วัดผลการตรวจด้วยชุดทดสอบที่ปลอดภัยและทำซ้ำได้

# 1. วิสัยทัศน์ผลิตภัณฑ์

### Product vision

> **Luna Guard เป็นเครื่องมือตรวจสอบความปลอดภัยและตอบสนองต่อไฟล์ที่น่าสงสัย ช่วยให้ผู้ใช้เห็นหลักฐาน เข้าใจความเสี่ยง และแยกไฟล์ออกจากการใช้งานได้อย่างปลอดภัย**

ผลิตภัณฑ์ไม่ได้มีหน้าที่เพียง “สแกนไวรัส” แต่ต้องช่วยให้ผู้ใช้:

- เริ่มตรวจสอบได้โดยไม่ต้องมีความรู้ด้าน Cybersecurity สูง
- เข้าใจว่าโปรแกรมตรวจอะไรและใช้หลักฐานใด
- แยกความแตกต่างระหว่างผลตรงกับแฮช ผล YARA และ heuristic
- ตัดสินใจว่าจะกักกัน ตรวจสอบเพิ่ม หรือเพิกเฉยต่อผล false positive
- เรียกดูประวัติและย้อนตรวจสอบการดำเนินการได้
- ใช้ Luna Guard ร่วมกับเครื่องมือป้องกันที่มีอยู่ เช่น Microsoft Defender
- เข้าใจข้อจำกัดของแพลตฟอร์มและฟีด Threat Intelligence

### ผลลัพธ์ที่ผู้ใช้ควรได้รับ

เมื่อสิ้นสุดการสแกน ผู้ใช้ควรรู้คำตอบของคำถามต่อไปนี้:

1. สแกนอะไรและสแกนในขอบเขตใด?
2. มีไฟล์ใดถูกตรวจพบหรือข้ามไปบ้าง?
3. เหตุใดจึงจัดระดับความเสี่ยงเช่นนั้น?
4. ผลใดเป็นหลักฐานยืนยัน และผลใดเป็นเพียงสัญญาณให้ตรวจสอบเพิ่ม?
5. ขั้นตอนถัดไปที่ปลอดภัยคืออะไร?

# 2. ตำแหน่งและขอบเขตผลิตภัณฑ์

## 2.1 สิ่งที่ Luna Guard มุ่งหมายจะเป็น

- เครื่องมือตรวจไฟล์และสัญญาณที่น่าสงสัย
- เครื่องมือวิเคราะห์ไฟล์ด้วย YARA และกฎตรวจจับแบบออฟไลน์
- Client สำหรับดึงและใช้งาน Threat Intelligence/IOC
- เครื่องมือแสดงผลการตรวจสอบระบบ Windows ตามสิทธิ์ที่ได้รับ
- Quarantine manager ที่มีขั้นตอน Restore และ audit trail
- ผลิตภัณฑ์ open source สำหรับการเรียนรู้ วิจัย และใช้งานส่วนบุคคล
- Mobile companion สำหรับตรวจไฟล์ที่ผู้ใช้เลือกหรือโฟลเดอร์ Android ที่ผู้ใช้อนุญาต

## 2.2 สิ่งที่ Luna Guard ไม่ควรอ้างว่าเป็น

- สิ่งทดแทน Antivirus หรือ Microsoft Defender
- ระบบป้องกันแบบ real-time หากยังไม่มีความสามารถดังกล่าว
- Enterprise EDR หรือระบบตอบสนองเหตุการณ์ระดับองค์กร
- เครื่องมือที่รับประกันว่าจะกำจัดมัลแวร์ได้ทุกชนิด
- ระบบที่ตรวจพบภัยคุกคามได้ครบถ้วน 100%
- ระบบยืนยันการติดเชื้อจากชื่อไฟล์หรือ heuristic เพียงอย่างเดียว
- ระบบที่สแกนได้ทุกไฟล์ ทุก process หรือทุกพื้นที่ของทุกแพลตฟอร์ม

## 2.3 ข้อความแนะนำสำหรับผู้ใช้

> Luna Guard เป็นเครื่องมือตรวจสอบความปลอดภัยและตรวจจับไฟล์ที่น่าสงสัย โดยใช้กฎ YARA, Threat Intelligence และการตรวจสอบระบบตามขอบเขตที่ระบบอนุญาต โปรแกรมช่วยแสดงหลักฐานและกักกันไฟล์ แต่ไม่ใช่ Antivirus แบบ real-time และไม่รับประกันว่าจะตรวจพบภัยคุกคามทั้งหมด

### ขอบเขตตามแพลตฟอร์ม

| แพลตฟอร์ม | ขอบเขตที่ควรสื่อสาร |
|---|---|
| Windows Desktop | ความสามารถขึ้นกับโมดูลและสิทธิ์ของ Windows ที่ใช้งานจริง ต้องรายงานรายการที่ข้ามหรือไม่มีสิทธิ์อ่าน |
| Android | สแกนไฟล์ที่เลือก หรือไฟล์ภายในโฟลเดอร์ที่ผู้ใช้อนุญาตผ่าน Storage Access Framework (SAF) ไม่ใช่การสแกนทั้งเครื่อง |
| iOS | สแกนไฟล์ที่ผู้ใช้เลือกผ่านระบบ ไม่เข้าถึงข้อมูลส่วนตัวของแอปอื่น |

> ความสามารถของแต่ละแพลตฟอร์มต้องระบุแยกกัน ห้ามนำความสามารถของ Windows ไปสื่อว่า mobile app ทำได้เช่นเดียวกัน

# 3. ภาพรวมสถาปัตยกรรม

แผนภาพต่อไปนี้เป็น **ภาพเชิงแนวคิด** เพื่อช่วยวางขอบเขตโมดูล ไม่ใช่หลักฐานยืนยันว่าโค้ดทุกส่วนเชื่อมต่อกันหรือมีความสามารถครบตามนี้แล้ว

```text
┌────────────────────────────────────────────────────────────┐
│                       Luna Guard UI                         │
│ Dashboard · Scan · Results · Quarantine · History · Settings│
└──────────────────────────────┬─────────────────────────────┘
                               │
┌──────────────────────────────▼─────────────────────────────┐
│                 Local Application/API Layer                 │
│ Validation · Session Auth · Request Limits · Audit Events    │
└──────────────────────────────┬─────────────────────────────┘
                               │
┌──────────────────────────────▼─────────────────────────────┐
│                    Security/Scan Engine                      │
│ File I/O · SHA-256 · YARA · IOC · Archive Limits · System    │
└─────────────┬──────────────────┬─────────────────┬──────────┘
              │                  │                 │
       ┌──────▼──────┐    ┌──────▼──────┐   ┌──────▼──────┐
       │ YARA Rules  │    │ Threat Intel│   │ OS Inspection│
       │ Provenance  │    │ IOC Lifecycle│  │ Permissioned │
       └─────────────┘    └─────────────┘   └──────────────┘
                               │
┌──────────────────────────────▼─────────────────────────────┐
│                Results · SQLite · Audit Log                  │
└──────────────────────────────┬─────────────────────────────┘
                               │
                    ┌──────────▼──────────┐
                    │ Quarantine / Restore│
                    │ Verify · Recover    │
                    └─────────────────────┘
```

### แนวแบ่งความรับผิดชอบ

- **UI:** แสดงสถานะและส่งคำขอ ไม่ควรเป็นเจ้าของตรรกะตรวจจับหรือสิทธิ์ระบบ
- **API/Application layer:** ตรวจ input, authentication, authorization, ขนาด request และวิธี HTTP
- **Scan engine:** อ่านข้อมูลแบบจำกัดทรัพยากร ส่ง progress และรายงานผลบางส่วน/ข้อผิดพลาด
- **Threat intelligence:** เก็บ provenance, วันหมดอายุ, ความเชื่อมั่น และสถานะของ IOC
- **Storage:** ใช้ SQLite และไฟล์ metadata โดยมี schema/version/migration ที่ตรวจสอบได้
- **Quarantine:** แยกจากไฟล์ต้นฉบับ มีขั้นตอน commit/rollback และการตรวจ hash
- **Audit:** บันทึกการกระทำสำคัญโดยไม่เก็บ token, secret หรือเนื้อหาไฟล์เกินจำเป็น

# 5. ระบบจัดลำดับความสำคัญ

| ระดับ | ความหมาย | ตัวอย่างงาน |
|---|---|---|
| **P0 — Critical** | ลดความเสี่ยงต่อข้อมูลผู้ใช้หรือการควบคุมระบบ ต้องทำก่อนขยายการใช้งานสำคัญ | Quarantine/Restore, Local API, archive limits, secrets |
| **P1 — High** | เพิ่มความน่าเชื่อถือและลดการตรวจผิด/ตรวจไม่ครบ | benchmark, YARA lifecycle, scan audit, accessibility |
| **P2 — Medium** | เพิ่มความสมบูรณ์และความสะดวกในการดูแล | signing, onboarding, localization, rule management |
| **P3 — Future** | ความสามารถระยะยาวที่ต้องมีการประเมินความเสี่ยงและขอบเขตใหม่ | real-time research, cloud reputation, enterprise policy |

# 6. P0 — ความปลอดภัยของ Quarantine

## ความเสี่ยง

การย้ายไฟล์ก่อนบันทึก metadata อาจทำให้ระบบไม่สอดคล้องกัน หากโปรแกรมปิดกะทันหัน:

```text
ไฟล์ต้นฉบับ ──move──> พื้นที่ Quarantine
                              │
                              └── โปรแกรมปิดก่อนอัปเดต index
                                  → ไฟล์กำพร้า (orphaned file)
```

ตัวอย่างแนวทางที่ไม่ควรใช้เป็นขั้นตอนสมบูรณ์โดยลำพัง:

```python
shutil.move(source_path, destination_path)
update_index()
```

## ขั้นตอนที่แนะนำ

1. ตรวจว่า source เป็นไฟล์ปกติและอยู่ในขอบเขตที่ผู้ใช้ร้องขอ
2. บันทึก metadata ขั้นต้นและสร้าง quarantine ID ที่ไม่ซ้ำ
3. คำนวณ SHA-256 ของต้นฉบับ
4. ย้าย/คัดลอกไปยังชื่อชั่วคราวภายใน quarantine volume ที่ควบคุม
5. ปิดและ flush ไฟล์ข้อมูลตามความเหมาะสม
6. คำนวณ SHA-256 ปลายทางและเปรียบเทียบกับต้นฉบับ
7. เมื่อ hash ตรง ให้เขียน metadata ด้วยรูปแบบ atomic
8. เปลี่ยนสถานะรายการเป็น `COMMITTED` และบันทึก audit event
9. ตรวจสภาพกู้คืนหลังเริ่มโปรแกรมใหม่ และจัดการรายการที่ค้างตามสถานะ
10. หากขั้นตอนใดล้มเหลว ให้ rollback เท่าที่ปลอดภัยและแจ้งผู้ใช้

> ห้ามลบไฟล์ต้นฉบับหรือไฟล์ชั่วคราว หากยังยืนยันไม่ได้ว่าข้อมูลใน Quarantine สมบูรณ์และกู้คืนได้

## State machine ที่แนะนำ

```text
PENDING → COPYING/MOVING → VERIFYING → COMMITTED
    │           │              │
    └───────────┴──────────────┴──> FAILED / RECOVERY_REQUIRED
```

## เงื่อนไขรับงาน

- หลังจำลองการปิดโปรแกรมในแต่ละขั้น ระบบต้องตรวจพบรายการค้างได้
- ไฟล์ที่ commit แล้วต้องมี metadata และ SHA-256 ที่ตรงกัน
- ความล้มเหลวต้องไม่ทำให้ข้อมูลต้นฉบับหายโดยไม่มีสำเนาที่ตรวจสอบได้
- UI ต้องแสดงสถานะ `กำลังกักกัน`, `กักกันแล้ว`, `ต้องกู้คืนสถานะ` หรือ error ที่เหมาะสม
- มี unit/integration tests สำหรับความล้มเหลว การชนชื่อ และการปิดโปรแกรมกลางทาง

# 7. P0 — ความถูกต้องก่อน Restore

ก่อน Restore ต้องตรวจสอบอย่างน้อย:

- quarantine ID มีรูปแบบถูกต้องและมีอยู่ในฐานข้อมูล
- metadata อ่านได้และสัมพันธ์กับ ID/ไฟล์จริง
- ไฟล์ Quarantine มีอยู่จริงและอ่านได้
- SHA-256 ปัจจุบันตรงกับ hash ที่บันทึกไว้
- destination ผ่านการตรวจ path และไม่ชี้กลับเข้า Quarantine
- destination conflict ถูกจัดการด้วยการถามผู้ใช้ ไม่เขียนทับเงียบ ๆ
- parent directory ใช้งานได้และมีสิทธิ์เขียน

```text
คำขอ Restore
     ↓
ตรวจ ID และ metadata
     ↓
คำนวณ SHA-256 ของไฟล์ใน Quarantine
     ↓
เปรียบเทียบกับ hash ที่บันทึก
   ┌─ตรง──────────────→ ตรวจ path → Restore อย่างปลอดภัย
   └─ไม่ตรง/ตรวจไม่ได้──→ BLOCK → แจ้งเตือนและเก็บไฟล์ไว้
```

### เงื่อนไขสำคัญ

- หาก hash ไม่ตรง ให้ **หยุด Restore** และห้ามแก้ metadata เพื่อให้ผ่าน
- บันทึกเหตุการณ์ Restore ที่สำเร็จ/ล้มเหลวโดยไม่บันทึกข้อมูลลับ
- แสดงข้อความให้ผู้ใช้ทราบว่าไฟล์ที่ Restore อาจกลับมาเข้าถึงได้โดยระบบ

# 8. P0 — การตรวจสอบ Restore path

ห้ามเชื่อ path จาก request หรือ metadata โดยไม่ตรวจสอบ

### รายการตรวจสอบ

- เป็น absolute path ตามรูปแบบ Windows ที่ถูกต้อง
- ไม่ใช่ root หรือ path ที่ห้ามเขียนตาม policy
- ไม่ชี้เข้า quarantine directory หลัง normalize path
- ตรวจ parent directory และสิทธิ์การเขียน
- ตรวจ destination ซ้ำก่อนเริ่มและก่อน finalize เพื่อลด race condition
- ป้องกัน path traversal, alternate path syntax และ reparse point ตาม threat model
- ไม่เขียนทับไฟล์ที่มีอยู่โดยไม่ได้รับคำยืนยันชัดเจน

หากตำแหน่งเดิมใช้ไม่ได้ ให้แสดง:

> **ไม่พบตำแหน่งเดิมของไฟล์**  
> เลือกโฟลเดอร์ปลายทางใหม่ หรือยกเลิกการ Restore

การเลือกตำแหน่งใหม่ต้องทำผ่าน UI ที่ตรวจ path ซ้ำ และต้องเก็บ original path แยกจาก destination ปัจจุบันใน metadata

# 9. P0 — ความปลอดภัยของ Local API

การ bind ที่ `127.0.0.1` ช่วยลดการเปิดบริการสู่เครือข่าย แต่ **ไม่ใช่มาตรการป้องกันครบถ้วน** เพราะเว็บเบราว์เซอร์หรือ process อื่นในเครื่องเดียวกันอาจพยายามส่งคำขอได้

## ข้อกำหนด

- bind เฉพาะ loopback interface ที่จำเป็น ไม่ bind `0.0.0.0`
- ตรวจ `Host` และ `Origin` ด้วย allowlist ที่ชัดเจน
- ใช้ token ที่สุ่มต่อ session และส่งผ่าน header ไม่ใส่ใน URL
- เปรียบเทียบ token ด้วย constant-time comparison
- กำหนด endpoint และ HTTP method แบบ allowlist
- ตรวจ `Content-Type`, schema, ชนิดข้อมูล และขนาด body
- ใช้ rate limit และ timeout สำหรับ endpoint ที่ใช้ทรัพยากรมาก
- ปฏิเสธ method/route ที่ไม่รองรับด้วย status code ที่เหมาะสม
- ไม่เปิด CORS กว้างโดยไม่จำเป็น
- ไม่สะท้อน input ที่ยังไม่ sanitize กลับเข้า UI
- ไม่บันทึก token, secret หรือ request body ที่มีข้อมูลละเอียดอ่อน
- ทดสอบ CSRF/DNS rebinding และการยิง request จาก origin ที่ไม่ได้รับอนุญาต

## รูปแบบ Authentication ที่แนะนำ

หลีกเลี่ยง token ใน query string:

```http
GET /api/action?token=SECRET
```

ใช้ header ผ่าน channel ที่กำหนด:

```http
POST /api/action
Host: 127.0.0.1:<port>
X-Luna-Token: <session-token>
Content-Type: application/json
```

Token ต้องไม่ปรากฏใน URL, browser history, referrer หรือ log

## เงื่อนไขรับงาน

- request ที่ไม่มี token, ใช้ token ผิด, Host/Origin ไม่ผ่าน หรือ body เกิน limit ต้องถูกปฏิเสธ
- endpoint ที่เปลี่ยนสถานะต้องไม่ตอบรับด้วย HTTP method ที่ไม่กำหนด
- มี automated security tests ครอบคลุม authorization, validation, limits และ error responses

# 10. P0 — ความปลอดภัยของ Archive

Archive อาจทำให้เกิด resource exhaustion, nested archive ที่ไม่สิ้นสุด, ไฟล์ขยายตัวสูง หรือ path traversal ระหว่างแตกไฟล์

## Hard limits ที่ต้องกำหนด

| Limit | จุดประสงค์ |
|---|---|
| `MAX_ARCHIVE_MEMBERS` | จำกัดจำนวน entry |
| `MAX_EXTRACTED_BYTES` | จำกัดข้อมูลรวมหลังคลายบีบอัด |
| `MAX_NESTING_DEPTH` | จำกัด archive ซ้อน |
| `MAX_SCAN_TIME` | จำกัดเวลาประมวลผลต่อ archive |
| `MAX_TEMP_DISK` | จำกัดพื้นที่ชั่วคราว |
| `MAX_FILE_SIZE` | จำกัดขนาด entry เดี่ยว |
| Compression ratio | ตรวจจับ zip bomb หรืออัตราขยายผิดปกติ |

ค่าตัวเลขต้องเลือกจากการทดสอบกับเครื่องเป้าหมาย และต้องระบุใน settings/เอกสารเมื่อผู้ใช้เปลี่ยนได้ ห้ามปล่อยให้ค่าไม่จำกัด

### ค่าที่ใช้ใน desktop scanner ปัจจุบัน

| Limit | ค่าปัจจุบัน | พฤติกรรมเมื่อเกิน |
|---|---:|---|
| จำนวน entry รวมใน archive tree | 10,000 | หยุดตรวจและระบุผลเป็น `INCOMPLETE` |
| ขนาดข้อมูลคลายบีบอัดต่อสมาชิก | 256 MiB | ข้ามสมาชิกและระบุผลเป็น `INCOMPLETE` |
| ข้อมูลคลายบีบอัดรวม/งบพื้นที่ชั่วคราว | 512 MiB | หยุดตรวจและระบุผลเป็น `INCOMPLETE` |
| ความลึก archive ซ้อน | 8 ชั้น | ข้าม archive ชั้นที่เกินและระบุผลเป็น `INCOMPLETE` |
| เวลาตรวจ archive tree | 180 วินาที | หยุดตรวจและระบุผลเป็น `INCOMPLETE` |

ค่าข้างต้นเป็นค่าคงที่ของ desktop scanner ไม่ใช่ค่าที่ผู้ใช้ปรับได้จากหน้า Settings และไม่ได้กำหนดเพดานขนาดไฟล์ปกตินอก archive

## ข้อกำหนดการประมวลผล

- อ่านแบบ streaming หากทำได้ ไม่โหลด archive ทั้งหมดเข้า RAM
- ตรวจ path ภายใน archive ก่อนเขียนไฟล์ ป้องกัน Zip Slip/path traversal
- ไม่ execute เนื้อหาจาก archive
- กำหนด cleanup ของ temporary files เมื่อสำเร็จ ยกเลิก หรือเกิด error
- หยุดอย่างปลอดภัยเมื่อเกิน limit และรายงานว่า scan ไม่ครบ
- เก็บจำนวน entry ที่ตรวจ ข้าม และล้มเหลวไว้ในผล audit

```text
Archive → ตรวจ header/metadata → ตรวจ limits → สแกนเป็น stream
                                      │
                   เกิน limit ───────┴──→ หยุด + รายงาน INCOMPLETE
```

# 11. P0 — ความปลอดภัยของ Build

การติดตั้ง dependency เวอร์ชันล่าสุดทุกครั้ง เช่น `pip install --upgrade ...` ทำให้ผล build เปลี่ยนตามเวลาและเพิ่มความเสี่ยงจาก supply chain

## แนวทางที่แนะนำ

- แยก runtime dependencies ออกจาก build dependencies
- pin เวอร์ชันที่ผ่านการทดสอบ และพิจารณา hash checking
- ใช้ lock file หรือ constraints file ตาม package manager
- อัปเดต dependency ผ่าน pull request ที่รัน tests และตรวจ changelog
- จำกัดสิทธิ์ของ CI token ให้เท่าที่จำเป็น
- ไม่เก็บ signing key/API secret ใน repository หรือ log
- สร้าง artifact จาก commit/tag ที่ระบุชัดเจน
- บันทึก SHA-256 ของ artifact และแนบให้ผู้ใช้ตรวจสอบ
- ใช้ code signing เมื่อมี certificate และกระบวนการจัดการ key ที่เหมาะสม

ตัวอย่างไฟล์ที่อาจใช้:

```text
requirements.txt          # Runtime dependencies
requirements-build.txt    # Packaging/build dependencies
constraints.txt           # Version constraints (ถ้าเหมาะสม)
```

ตัวอย่าง pin เป็นรูปแบบเท่านั้น ต้องแทนด้วยเวอร์ชันที่ทดสอบจริง:

```text
pywebview==<tested-version>
yara-python==<tested-version>
pyinstaller==<tested-version>
```

# 12. สถาปัตยกรรมการตรวจจับ

ใช้แนวทาง **Multi-layer detection** แต่แยกผลแต่ละชั้น ไม่รวมคะแนนจนผู้ใช้เข้าใจผิดว่าเป็น probability

```text
ไฟล์/วัตถุที่ตรวจ
   ├── SHA-256 reputation
   ├── YARA rules
   ├── Static indicators
   ├── Threat Intelligence / IOC
   └── System inspection (เฉพาะที่ platform และ permission รองรับ)
                 ↓
       ผลตรวจพร้อม evidence และข้อจำกัด
```

## หลักการรวมผล

- เก็บ finding แต่ละรายการพร้อม source/rule/evidence แยกจากกัน
- การ match แฮชที่เชื่อถือได้ไม่ควรถูกลดทอนด้วย heuristic ที่อ่อนกว่า
- heuristic หรือชื่อไฟล์ไม่ใช่หลักฐานยืนยันตระกูลมัลแวร์
- ไม่บวกคะแนนซ้ำจาก signature ที่ซ้ำหรือสัมพันธ์กันโดยไม่มีเหตุผล
- ผลที่ขาดข้อมูลต้องระบุ `Unknown`, `Incomplete` หรือ `Not checked` แทนการถือว่าสะอาด
- การจัดระดับต้องมีเอกสารและ regression tests
- ห้ามเรียกการลบหรือ quarantine อัตโนมัติโดยไม่มี policy ที่ชัดเจนและการป้องกันความเสียหาย

# 13. รูปแบบผลการตรวจจับ

ไม่ควรแสดงเปอร์เซ็นต์ เช่น `98% Malware` หากไม่ได้มาจากโมเดลทางสถิติที่ผ่านการตรวจสอบและอธิบาย calibration ได้

## ฟิลด์ที่แนะนำ

```text
scan_id
object_name
object_path (ถ้ามีและนโยบายอนุญาต)
sha256
size_bytes
scan_started_at
scan_finished_at
scan_status
risk_level
findings[]
sources[]
limitations[]
recommended_action
```

แต่ละ finding ควรมี:

```text
rule_id / signature_id
source
category
severity
confidence (เฉพาะเมื่อมีนิยาม)
matched_evidence (จำกัดและ sanitize)
first_seen / last_seen (สำหรับ IOC)
rule_version
reference
```

## ภาษาที่แนะนำ

```text
Risk level: HIGH
Detection source:
• SHA-256 reputation match
• YARA rule: <rule-id>
• Suspicious PowerShell indicators
```

ให้แยกความหมายของ **Risk level**, **Detection strength** และ **Confidence** และนิยามไว้ก่อนนำไปใช้บน UI

# 14. สถาปัตยกรรม YARA

แบ่งกฎตามหน้าที่และความน่าเชื่อถือ ไม่รวม community rules และ custom rules โดยไม่มี provenance

```text
rules/
├── core/
│   ├── powershell.yar
│   ├── ransomware.yar
│   └── trojan.yar
├── families/
│   └── xworm.yar
├── community/
└── custom/
```

โครงสร้างเป็นข้อเสนอ สามารถปรับให้สอดคล้องกับ repository จริงได้

## Metadata ต่อกฎ

# 16. วงจรชีวิต IOC

IOC ไม่ควรถูกเก็บเป็น active ตลอดไป เพราะข้อมูลอาจเก่า ผิดบริบท หรือหมดประโยชน์

```text
ACTIVE → STALE → EXPIRED → ARCHIVED/REMOVED
```

### กฎการเปลี่ยนสถานะ

- **ACTIVE:** ยังอยู่ในช่วงเวลาและระดับความเชื่อมั่นที่กำหนด
- **STALE:** ไม่ได้รับการยืนยันใหม่ตามช่วงเวลาที่กำหนด
- **EXPIRED:** หมดอายุ ห้ามใช้เป็นหลักฐานปัจจุบันโดยไม่แสดงคำเตือน
- **ARCHIVED/REMOVED:** เก็บเพื่อ audit หรือเอาออกตามนโยบาย retention

ต้องบันทึก `first_seen`, `last_seen`, `expires_at`, source และเหตุผลที่เปลี่ยนสถานะ การลบข้อมูลตาม retention ต้องไม่ทำลาย audit ที่จำเป็นต่อการตรวจสอบย้อนหลัง

# 17. SQLite และการจัดเก็บข้อมูล

SQLite เหมาะกับแอปพลิเคชัน local แบบผู้ใช้รายเดียว หากปริมาณการเขียน/จำนวนผู้ใช้ไม่ต้องการฐานข้อมูล server

ตารางที่แนะนำ:

| ตาราง | หน้าที่ |
|---|---|
| `hashes` | ค่า hash และ metadata ของแหล่งข้อมูล |
| `iocs` | IOC, provenance และ lifecycle |
| `meta` | schema version และข้อมูลระบบ |
| `allow` | รายการ allowlist พร้อมเหตุผลและขอบเขต |
| `scan_history` | สรุปการสแกนและผล |
| `quarantine` | สถานะ/metadata ของรายการ Quarantine |
| `audit_log` | เหตุการณ์สำคัญที่จำเป็นต่อการตรวจสอบ |

### ข้อกำหนดด้านข้อมูล

- ใช้ schema version และ migration ที่ทดสอบได้
- กำหนด index/constraint และ transaction สำหรับการเปลี่ยนสถานะสำคัญ
- จัดการ backup/recovery และความเสียหายของฐานข้อมูล
- ใช้ retention ที่จำกัดข้อมูลเกินจำเป็น
- ไม่บันทึก API secret, token หรือเนื้อหาไฟล์โดยไม่จำเป็น
- เวลาควรเก็บเป็นรูปแบบมาตรฐาน เช่น UTC/ISO 8601 พร้อมระบุ timezone
- แยกผล scan, IOC feed state และ Quarantine metadata ให้ชัดเจน

ฟิลด์ประกอบที่ควรพิจารณา:

```text
created_at
updated_at
source_version
last_seen
schema_version
```

# 19. Detection Benchmark

แยก benchmark corpus ออกจาก unit tests และห้ามเผยแพร่ตัวอย่างมัลแวร์จริงใน repository สาธารณะโดยไม่มีนโยบายควบคุมและเหตุผลที่ผ่านการทบทวน

### หมวดชุดทดสอบ

- **Benign:** ไฟล์ปกติและซอฟต์แวร์ที่ได้รับอนุญาต
- **Suspicious:** ตัวอย่างจำลองหรือไฟล์ที่มีพฤติกรรมคล้ายกันเพื่อทดสอบ heuristic
- **Known detection:** hash/signature ที่มี provenance และสิทธิ์ใช้งานชัดเจน
- **False-positive candidates:** ไฟล์ที่มีชื่อ/สตริงคล้ายภัยคุกคาม เช่น component ของเกมหรือโปรแกรมทั่วไป

### Metrics

```text
True Positive (TP)
False Positive (FP)
False Negative (FN)
Precision = TP / (TP + FP)
Recall/Detection Rate = TP / (TP + FN)
Scan time and resource usage
```

ต้องระบุชุดข้อมูล เวอร์ชันกฎ และวิธีคำนวณทุกครั้ง ผล benchmark เป็นของชุดข้อมูลนั้นเท่านั้น ไม่ใช่หลักประกันว่าจะตรวจพบทุกภัยคุกคามจริง

# 20. กลยุทธ์การทดสอบ

ชุดทดสอบควรครอบคลุม:

- **Unit tests:** parser, scoring, hashing, validation, state transitions
- **Integration tests:** scan → result → history, Quarantine → verify → Restore
- **Security tests:** path traversal, auth, request limits, archive limits, secret leakage
- **Regression tests:** ปัญหาที่เคยพบและ false positive ที่ยืนยันแล้ว
- **Performance tests:** ไฟล์ใหญ่, archive จำนวนมาก, cancellation และ memory ceiling
- **UI/API tests:** keyboard flow, error states, endpoint authorization
- **Platform tests:** Windows รุ่นที่รองรับ และ mobile permissions ตามระบบ

ก่อน release ให้ CI รันชุดทดสอบที่เกี่ยวข้องและเก็บผลจาก commit เดียวกับ artifact ทุกครั้ง

# 22. Code Signing และการเผยแพร่

ไฟล์ EXE ที่ไม่ได้ลงลายเซ็นอาจแสดงคำเตือนจาก Windows SmartScreen ทั้งนี้ลายเซ็นไม่ได้รับประกันว่าโปรแกรมปลอดภัย แต่ช่วยยืนยันตัวผู้เผยแพร่และความสมบูรณ์ของไฟล์ตาม certificate

```text
Build → Test → Generate SHA-256 → Sign (ถ้ามี)
      → Verify signature → Publish artifact + release notes
```

Checklist:

- certificate/key เก็บใน secret store ที่เหมาะสม ไม่ commit ลง repository
- จำกัดผู้เข้าถึง signing credentials
- ตรวจลายเซ็นหลังลงนาม
- สร้าง SHA-256 ของ artifact ที่เผยแพร่
- ผูก artifact กับ tag/commit และ build run
- release notes ระบุ known limitations และวิธีรายงานปัญหา

หน้าผลตรวจควรตอบ:

1. **พบอะไร?** ชื่อ detection ที่ระมัดระวัง
2. **อยู่ที่ไหน?** path/ชื่อไฟล์ตามสิทธิ์และนโยบาย
3. **ทำไมจึงแจ้งเตือน?** rule, IOC หรือหลักฐาน
4. **ระดับความเสี่ยงใด?** อธิบายความหมาย
5. **ควรทำอะไรต่อ?** แนะนำทางเลือกที่ปลอดภัย

```text
HIGH RISK — ต้องตรวจสอบ
พบไฟล์ที่ตรงกับหลักฐานจาก <แหล่งตรวจ>

ชื่อ: sample.exe
ตำแหน่ง: <path>
ตรวจด้วย: YARA <rule-id>, SHA-256 reputation
SHA-256: <hash>

คำแนะนำ: กักกันเพื่อแยกไฟล์ออกจากการใช้งาน
[กักกัน]  [ดูรายละเอียด]
```

หากเป็น heuristic:

```text
พบรูปแบบที่น่าสงสัย — ยังไม่ใช่การยืนยันว่าติดเชื้อ
```

# 32. “ทำไมไฟล์นี้จึงถูกตรวจพบ?”

แสดงคำอธิบายภาษาทั่วไป พร้อมรายละเอียดทางเทคนิคแบบขยายได้

```text
เหตุผลที่แจ้งเตือน
พบสัญญาณ PowerShell หลายรายการที่มักใช้ร่วมกับสคริปต์ดาวน์โหลด/ซ่อนการทำงาน

หลักฐาน:
• พบการถอดรหัส Base64
• พบการดาวน์โหลดข้อมูลจากเครือข่าย
• พบตัวเลือกซ่อนหน้าต่าง

ข้อจำกัด:
การจับคู่จากสตริงไม่ยืนยันว่ามีการเรียกใช้จริง
```

ข้อกำหนด:

- แยก “สิ่งที่พบ” ออกจาก “การตีความ”
- ระบุ rule/source/version และ reference เมื่อมี
- อธิบาย false-positive caveat
- ไม่แสดงข้อมูลเทคนิคดิบเป็นคำตอบเพียงอย่างเดียว

# 49. Checklist ก่อนเผยแพร่

## Security

- [ ] Quarantine มี state/rollback และตรวจสอบความสมบูรณ์
- [ ] Restore ตรวจ hash และ path
- [ ] Local API จำกัด Host/Origin/auth/method/body
- [ ] Archive มี limits และป้องกัน path traversal
- [ ] ไม่มี secret ใน log, repository หรือ artifact
- [ ] Error ไม่ทำให้ UI รายงานผลสำเร็จผิด
- [ ] ตรวจ threat model ของ feature ที่เพิ่มใหม่

## Detection

- [ ] ทบทวน YARA rule, provenance และ license
- [ ] Threat Intelligence มี timeout, version และ lifecycle
- [ ] IOC expiration ทำงานตามที่กำหนด
- [ ] มี benchmark พร้อม dataset/version ที่ระบุ
- [ ] ทดสอบ false positive และ false negative
- [ ] ผลตรวจไม่กล่าวเกินหลักฐาน

## Testing

- [ ] Unit tests
- [ ] Integration tests
- [ ] Security tests
- [ ] Regression tests
- [ ] Performance/resource-limit tests
- [ ] UI/API tests
- [ ] ทดสอบบน environment ที่สะอาดและแพลตฟอร์มที่รองรับ

## UX/UI

- [ ] Dashboard แสดงสถานะและ action ถัดไป
- [ ] Scan flow ระบุ scope
- [ ] Threat detail อธิบายหลักฐาน
- [ ] Quarantine/Restore/Delete มี confirmation ที่เหมาะสม
- [ ] History และสถานะ incomplete ชัดเจน
- [ ] Empty/error/loading states ครบ
- [ ] Keyboard, contrast, scaling และ responsive ผ่านการตรวจ

## Release

- [ ] Version/tag ตรงกับ source
- [ ] Build/test ผ่านจาก commit เดียวกับ artifact
- [ ] Dependencies ถูกควบคุมเวอร์ชัน
- [ ] สร้าง SHA-256 ของ artifact
- [ ] Code signing/verification ทำเมื่อพร้อม
- [ ] GitHub Release มี changelog, known limitations และ download ที่ถูกต้อง
- [ ] เอกสาร Privacy/Security และช่องทางรายงานปัญหาเป็นปัจจุบัน

# 50. Roadmap

Roadmap นี้เป็น **milestones เชิงข้อเสนอ** ไม่ใช่หมายเลข release ที่ประกาศแล้ว ให้กำหนด release version จริงแยกตามแผนงานและผลทดสอบ

## Milestone A — Foundation hardening

- Quarantine/Restore integrity
- Local API hardening
- Archive resource limits
- Dependency pinning
- Error handling และ audit

**ผ่านเมื่อ:** tests ด้าน security/recovery ผ่าน และสถานะ failure แสดงต่อผู้ใช้ได้

## Milestone B — UX/UI

- Dashboard และ scan scope
- Progress/cancellation
- Threat detail และ “Why detected?”
- Quarantine, History, Settings
- Accessibility และ responsive layout

**ผ่านเมื่อ:** งานหลักทำได้ด้วย keyboard และผู้ใช้เข้าใจผล/ขั้นตอนถัดไปจากข้อความบนหน้าจอ

## Milestone C — Detection quality

- YARA architecture/provenance
- IOC lifecycle
- Benchmark และ false-positive tuning
- Detection audit/report

**ผ่านเมื่อ:** benchmark ทำซ้ำได้และแต่ละ detection เชื่อมโยงกับ source/version ได้

## Milestone D — Release engineering

- CI/CD tests
- Reproducible/pinned build
- Artifact hashes
- Signing และ signature verification เมื่อมี
- Release notes/known limitations

**ผ่านเมื่อ:** artifact เชื่อมโยงกับ commit/tag และมีหลักฐานตรวจสอบผล pipeline

## Milestone E — Advanced security research

- Behavioral indicators
- Rule management เพิ่มเติม
- Memory/system inspection ภายใต้ threat model และ permission ที่ชัด
- Cloud reputation/enterprise features หลังผ่าน privacy/security review

**ผ่านเมื่อ:** มี threat model, consent/privacy review, abuse cases และ resource limits

- [ ] ปิดโปรแกรมกลางทางแล้วกู้สถานะได้
- [ ] Restore ตรวจ hash/path และจัดการ conflict
- [ ] Delete ต้องผ่าน confirmation
- [ ] UI แสดงสถานะและ error ที่เข้าใจได้
- [ ] มี tests ทั้ง success, failure, rollback และ recovery
- [ ] เอกสารและ audit fields เป็นปัจจุบัน

# 57. บทสรุป

Luna Guard มีแนวคิดและองค์ประกอบหลายด้านที่สามารถต่อยอดได้ เช่น YARA, Threat Intelligence, archive scanning, process/system inspection, Quarantine, SQLite, Local API, scan audit, automated tests และ desktop/mobile applications

การมีองค์ประกอบเหล่านี้ไม่ได้ยืนยันโดยตัวมันเองว่าทุกฟีเจอร์ทำงานครบหรือปลอดภัยแล้ว ขั้นตอนต่อไปจึงควรมุ่งไปที่:

- ยืนยันความสามารถจริงจากโค้ดและผลทดสอบ
- ลดความเสี่ยงใน Quarantine, Restore, API และ Archive
- แสดงสถานะ incomplete/unknown อย่างตรงไปตรงมา
- สร้าง benchmark และ regression coverage
- ทำให้ build/release ตรวจสอบย้อนกลับได้
- ออกแบบประสบการณ์ใช้งานที่ช่วยให้ตัดสินใจได้โดยไม่สร้างความตื่นตระหนก

เป้าหมายระยะยาว:

> **จากโครงการความปลอดภัยส่วนบุคคล สู่ผลิตภัณฑ์ความปลอดภัยแบบ open source ที่น่าเชื่อถือ ตรวจสอบได้ และใช้งานอย่างรับผิดชอบ**

## ภาคผนวก A: คำศัพท์

| คำ | ความหมายในเอกสารนี้ |
|---|---|
| **IOC** | Indicator of Compromise เช่น hash, domain, URL หรือ IP ที่เชื่อมโยงกับกิจกรรมคุกคาม |
| **YARA rule** | กฎจับคู่รูปแบบในไฟล์หรือข้อมูล ไม่ใช่คำรับรองว่าไฟล์เป็นอันตรายเสมอ |
| **False positive** | ไฟล์ปกติถูกแจ้งเตือนว่าอาจน่าสงสัย |
| **False negative** | ภัยคุกคามที่มีอยู่แต่ระบบไม่ตรวจพบ |
| **Quarantine** | พื้นที่แยกไฟล์ออกจากการใช้งานปกติ โดยยังรักษาความสามารถในการตรวจสอบ/กู้คืน |
| **Atomic operation** | การเปลี่ยนสถานะที่สำเร็จครบหรือไม่เปลี่ยนเลยในมุมมองของระบบ |
| **Provenance** | แหล่งที่มาและประวัติของข้อมูลหรือกฎ |
| **SAF** | Android Storage Access Framework สำหรับให้ผู้ใช้เลือกและอนุญาตการเข้าถึงไฟล์/โฟลเดอร์ |
| **Incomplete** | การสแกนไม่ครอบคลุมตาม scope ที่ร้องขอ จึงสรุปว่า clean ไม่ได้ |
